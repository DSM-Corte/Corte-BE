# 유저 리뷰 답글에 이모티콘 반응 추가

- 이슈: #65

## 기능

원래 줄 코멘트나 전체 댓글을 쓴 유저와 관리자는 해당 코멘트의 답글에 반응을 추가할 수 있다.
반응을 단 유저와 관리자는 반응 하나를 삭제할 수 있다. 모든 API는 로그인해야 한다.

| 메서드 | 경로 | 계약 |
| --- | --- | --- |
| POST | /api/review-requests/{requestId}/replies/{replyId}/reactions | type을 받아 201, Location과 id, type, userId 반환 |
| DELETE | /api/review-requests/{requestId}/replies/{replyId}/reactions/{reactionId} | 반응 삭제 후 204 |

- 종류는 HEART, THUMBS_UP, SMILE, CELEBRATION이다. API와 도메인은 enum을 사용하고 DB에는 이름을 VARCHAR로 저장한다. 종류 추가에 DB 값 목록 변경이 필요하지 않다.
- 답글 응답에 reactionCounts(종류별 개수)와 reactions(삭제 대상 식별용 id, type, userId)를 추가한다. 반응이 없으면 빈 객체와 빈 배열이다.
- 닫힌 요청은 기존 답글 조회 권한을 유지한다. 조회 권한이 있더라도 반응 쓰기는 제한한다.
- 기존 사용자 리뷰의 검사 순서를 따른다. 요청 접근 → 하위 리소스 존재 → 반응 권한 → 닫힘 순서다.
  닫힌 요청의 일반 요청자가 다른 사람의 답글 반응을 취소하려 하면 권한 오류 R016이 먼저 발생한다.
  요청자가 관리자이거나 자신의 반응에 대한 취소 권한이 있으면 닫힘 오류 R010을 반환한다.
- 오류: 기존 요청 접근 R001(404), 답글 없음 R002(404), 닫힘 R010(409), 잘못된 종류 C001(400).
  반응 없음 R015(404), 반응 변경 권한 없음 R016(403), 같은 반응 중복 R017(409).
- 신규 테이블 review_reply_reactions에 답글, 추가한 회원, 종류를 저장한다. 기존 답글 변경은 없다.
- 동일 답글·회원·종류 조합을 DB 유니크 제약으로 보호한다. 반응 쓰기는 요청 행과 답글 행을 순서대로 잠근다. 리뷰 닫기의 UPDATE와 반응 쓰기가 같은 요청 행에서 직렬화된다.
- 답글 직접 삭제와 부모 코멘트 삭제 시 반응도 DB 외래 키로 정리한다.
- 답글 목록의 반응은 답글 ID 단위로 일괄 조회한다. 기존 목록 페이징을 따른다.
- 범위 밖: 프론트엔드 화면.

## MySQL 실행 검증과 독립 리뷰

- MySQL 8.4.13에서 Spring Boot JAR를 띄우고 PowerShell Invoke-WebRequest로 호출했다. 종료 코드 0.
- 원래 코멘트 작성자와 관리자의 추가 201, 일반 사용자의 변경 403 R016, 관리자 취소 204, 답글 조회 집계, 코멘트 삭제 후 반응 행 0건을 확인했다.
- 동일 사용자·답글·종류의 두 HTTP 요청을 동시에 보내자 201과 409 R017을 받고 반응 한 건만 저장됐다.
- MySQL에서 요청 닫기 UPDATE가 행 잠금을 잡은 상태로 별도 HTTP 반응 요청을 보내자 커밋 후 404 R001을 반환하고 반응은 저장되지 않았다.
- SHOW CREATE TABLE로 type 컬럼의 VARCHAR(20), 값 목록 CHECK 제약 없음, 유니크 키, 답글 외래 키 삭제 연쇄를 확인했다.
- 독립 리뷰에서 지적한 종료 경합은 요청 행 잠금으로 해결했고, 조회·권한·오류·삭제 케이스를 보강했다.
- 검증 결과와 다른 오류 우선순위가 적용되지 않도록 기존 리뷰 규칙을 명세에 기록했다.
- 저장소 테스트는 실제 DB 유니크 제약 위반의 R017 변환을 검증한다. MySQL별 락 동작은 별도 실행으로 재현했으며 H2 테스트에 타이밍 의존 병렬 시나리오를 추가하지 않았다.
